# ADR 0002: DevOps Persona — Gitflow Release Coordination with Worktree Isolation and Scheduled CI Lineage

## Status

Proposed

## Context

The `devops` persona orchestrator (issue #65) coordinates gitflow-based releases, maintains CI/CD pipelines, and spawns clean-context subagents (`scaffold-ci-cd`, `create-release`, `create-hotfix`) with full isolation from the developer's working tree. Three tensions motivated this ADR:

1. **Release coordination is a write-side, version-control-spanning operation.** Unlike QA's read-only audits, release and hotfix work mutates branches, tags, and Change Proposals across `main`/`develop`. Without an enforced execution boundary these mutations could leak into the developer's tree. ADR-0001 established the transient-worktree pattern for `qa`; release/hotfix operations are write-heavy and need the same isolation, plus an explicit cleanup discipline because every branch/tag operation happens against a worktree path.

2. **ADR-0001 left the scheduled/nightly lineage deliberately out of scope.** The `devops` issue explicitly names "gitflow with nightly builds". Nightly/scheduled builds are a CI-pipeline scheduling concern, not an agent runtime concern. This ADR extends ADR-0001's scope note: a scheduled lineage now enters the picture but is owned by pipeline configuration (`scaffold-ci-cd` output: GitHub Actions `schedule` / GitLab scheduled pipelines), complementing pull-based trigger events, never an agent sleeping in the runtime.

3. **Deployment reports need a classification token.** The persona emits release/deployment coordination reports. `[Scope: Artefact]` in `agent-markup` had no value for these; a new `Deployment` value is required so downstream parsers can classify CI/CD and release reports.

## Decision

1. **Worktree isolation is mandatory for all release/hotfix/CI operations** — the persona and its leaves create a transient git worktree per session under OS temp (`/tmp/devops-<session-id>`), materialise the relevant base (`develop` | `main`), and run every branch, version, changelog, tag, and merge operation inside it. The worktree MUST be removed on completion, error, or early termination (record + force-remove on failure). The developer working tree is never modified. This reuses ADR-0001's transient vs. persistent-state distinction: worktrees are execution context, never the agent-state store.

2. **Gitflow lineage with pipelined deploy triggers.** Standard gitflow branches (`develop` integration → `release/<version>` → `main` production; `hotfix/<slug>` derived from `main`, merged back to `main` + `develop`). Deploy triggers are expressed as CI/CD pipeline jobs (PR-stage basic validation; develop-merge integration + testing-stage deploy; main-merge production deploy) authored by `scaffold-ci-cd`, not as agent actions.

3. **Scheduled lineage is a pipeline-scheduling decision, not an agent loop.** Nightly builds are encoded in `scaffold-ci-cd` output only, and only on explicit request. This supersedes ADR-0001's "scheduled lineage out of scope" clause for the DevOps context.

4. **`[Scope: Artefact: Deployment]`** is added to the `agent-markup` enumeration for CI/CD and release coordination reports.

## Consequences

- **Positive:** Release/hotfix operations are isolated, deterministic, and auditable; the write-side surface (branches, tags, Change Proposals) is confined to a removable worktree; the persona is hands-off — it sequences leaves and gates rather than running pipelines; deployment artefacts are machine-classifiable. Reuses the QA Release-gate for approval, keeping one regression authority.
- **Negative:** Requires push permissions to `main`/`develop` and a maintained CI runner fleet for scheduled stages; worktree lifecycle discipline is load-bearing — a leaked worktree is a state-hygiene violation; nightly builds add runner cost and are opt-in.
- **Implementation Notes:** Encode the decision in the `devops` SKILL.md (PHASE 2 isolation, PHASE 4 stages, PHASE 5 cleanup) and its leaf skills. Bump `metadata.version` on each change. Add `Deployment` to `[Scope: Artefact]` in `agent-markup`. Revisit if a true agent-driven (non-CI) scheduled execution is ever required, since that remains out of scope here.
