# ADR 0001: QA Persona — Scope Modes and Transient Worktree Execution

## Status

Proposed

## Context

The `qa` persona orchestrator (issue #64) runs QA audits on demand with full isolation from the developer's working tree. Three tensions motivated this ADR:

1. **QA-practice split vs agent economics.** Standard QA splits verification by point-in-time: incremental/nightly feedback during development vs a consolidated end-of-release regression sweep. For an agent the marginal cost of re-running an audit is near-zero, so the mechanical rationale for *scheduling* a separate nightly build collapses. What remains meaningful is the scope decision: audit the delta (change + its Seams) during development vs sweep the full surface at a release gate. Without an explicit scope-mode decision the persona defaults to one undifferentiated run.

2. **Regression needs a baseline.** A full regression sweep asserts "no regression" relative to *something*. This repo's verification baseline is the Minimum Verification Surface Baseline resolved by the test-coverage audit. Issue #64 deliberately keeps `qa` independent of `analyze-a-codebase`/blueprint artefacts; the ADR needs to pin what a release-gate statement is anchored to without pulling in blueprint/analysis modules.

3. **Git worktree vs the state-persistence rule.** AGENTS.md forbids the agent-state store from falling back to volatile OS temp (`${TMPDIR}`/`/tmp`) because state governing escalation, competency, or progress must survive OS cleanup/reboots. A `git worktree` created for execution (tests, simulations, remediation) is transient execution context, not persistent state, but the rule as written created ambiguity about whether `/tmp` worktrees were sanctioned.

## Decision

1. **Scope modes are part of the `qa` skill definition**, selected from invocation context:
   - **Delta mode** (default, post-change): audit the change and its Seams — the diff, its Interfaces, and the tests touching them. Adversarial edge-case and unhappy-path hunting on the change surface. Current-code-state only.
   - **Release-gate mode** (end of release / before a gate): full-surface sweep. Regression statements MUST be anchored to the resolved Minimum Verification Surface Baseline and carry `[Confidence: Level]`. If no baseline exists, the persona states that explicitly rather than asserting "no regression".
2. **Transient git worktree execution is explicitly permitted** — including in OS temp (`/tmp/qa-<session-id>` and equivalents) — for the duration of a session for tests, simulations, and remediation. The AGENTS.md volatile-temp prohibition applies to the *persistent agent-state store* (escalation/competency/progress state), not to short-lived execution sandboxes. Worktrees MUST be removed on clean shutdown, including on error or early termination.

## Consequences

- **Positive:** The persona's behavior is calibrated and auditable; release-gate claims are baseline-anchored and confidence-tagged; `qa` can safely use cheap transient worktrees without colliding with the state-persistence policy; unblocks Writer and DevOps personas with the same pattern.
- **Negative:** The scope-mode branch adds a small calibration step at invocation; project teams must maintain their Minimum Verification Surface Baseline for release-gate mode to be meaningful.
- **Implementation Notes:** Encode the mode selection in the `qa` SKILL.md orchestration flow and the acceptance criteria in issue #64. Bump the skill's `metadata.version` on the change. Revisit this ADR (or add a new one) if a scheduled/nightly lineage is ever added to this repo, since that decision deliberately remains out of scope here.
